# Assessment of the independent Magic Fusion plan review

14 November 2026. Research assessment; no gameplay code or package was changed during that assessment. See [implementation status](FUSION_IMPLEMENTATION.md).

The review contains useful engineering suggestions, several already-covered requirements, and some incorrect mechanical claims. I checked it against the **complete** original plan, the unchanged current development revision `6cf42818ade856814003ac0cab8872795d884ffd`, existing fixtures and the supplied game's IL. The revised plan remains grounded in that evidence.

The reviewer explicitly says its input stopped before the native contracts and later slices. Those sections exist in the original 45,850-byte document. Support/caster effects, marginal overlapping control, complete rejection reasons, native construction rules, bounded caches and in-game validation were already included. The review's missing sections cannot be treated as omissions from the full plan. I retained revision 1 so the changes are reviewable.

## Decisions on the individual critiques

| Review item | Finding | Change to the plan |
| --- | --- | --- |
| **2.1: risk of a parallel scoring engine** | Valid architectural concern. The original plan already required shared primitives, but the boundary needed more explicit acceptance criteria. Native Fusion adapters are still legitimate; forbidding every Fusion-specific function would also forbid its actual dice-cap/save semantics. | Define the split: native configuration/occurrence interpretation and orchestration may be specialized; numerical damage/save/immunity/control/risk primitives are shared. Use representative ordinary-action regression cases, with explicit expected differences for intentional common bug fixes. Do not build a fake full-game replay engine solely to obtain golden scores. |
| **2.2: support fusions missing** | Not an omission: F8 already included caster/support effects, Vampiric Touch and Arcana Theft. The review did not receive F8. There is merit in making the scope prominent and separating simple support from secondary-area work. The supplied 60-source list does not justify inventing ordinary Cure combinations. | Add explicit F4S for verified simple helpful/caster-side cases, ranked by actual configurations. Keep complex cross-recipient/caster dependencies with the later mechanism work. Use existing asymmetric heal/buff/ally-harm rules, not a sign-flipped enemy score. |
| **2.3: additional area requires a second player-chosen aim** | **Incorrect for the inspected native path.** `AbilityData.GetDeliverBlueprint(true)` returns optional area metadata; `AbilityExecutionProcess.ProcessRoutine` uses the selected primary delivery and separately invokes clicked-target actions with the same execution context. There is one `ClickedTarget`, not two independent player choices. | Explicitly model multiple derived footprints under one native aim. Add candidate fields only for native freedoms that actually exist. Do not add a two-aim Cartesian search. |
| **2.3: clicked-target payload needs a second target/potential second action** | **Not implied by this component.** `AdditionalAbilityEffectRunActionOnClickedTarget.Apply` opens the existing context's `MainTarget` scope and runs its actions. `AbilityExecutionContext.MainTarget` returns `ClickedTarget`. The inspected calls do not construct another player command or action payment. A contained child cast can require separate modeling, but that must come from its graph. | Preserve the native application schedule, subjects and execution multiplicity. Do not charge an invented second action or require an invented second target. Also do not universally deduplicate recipients across different native effect occurrences. |
| **2.3: geometry, allocation and nested saves are different mechanisms** | Valid, already reflected in the original slices. A correct cone footprint alone does not support a shared-HD payload. “Nested saves are always hardest” is not established; a bounded explicit save can be simpler than a persistent secondary area. | Make the capability distinctions explicit. F1 keeps HD/nested/secondary exclusions until their own slices qualify. Rank expansions by evidence, practical benefit, risk and cost, not an assumed universal complexity order. |
| **2.4: duration-aware marginal control and pending ledger** | Substantive refinement. The original plan required these semantics, but a clearer time-based rule will help implementation. A persistent ledger tied only to “this round” is inappropriate for both modes and can become stale. | Define a decision-local control-coverage view from existing buffs and live committed casts, using game-time expiry. Credit soft control after hard control ends, preserve replacement/refresh semantics and keep uncertain pending outcomes probabilistic. Share the underlying value helper with ordinary effects where applicable. |
| **2.5: `Both` wrongly discounts save-independent damage** | **The claimed current bug is contradicted by the code.** `FusionDamageFactor` returns 1 when the action has no applicable `HalfIfSaved`; existing Shocking Grasp and negative-level fixtures assert that behavior. `MakeSaveAlsoForMagicHack` controls a nested saving-throw action, not whether every damage action is halved. | Clarify two axes: root-outcome eligibility and the action's own reduction rule. `Both` means no failed/passed branch restriction, not automatically no save reduction. Add/retain regression coverage; do not “fix” the working path by removing native half-on-save behavior. Magic Missile is not in the supplied 60-source list; use the existing legal touch-plus-burst fixture for baseline coverage. |
| **2.6: fused metamagic may not be read** | **Already implemented for the inspected path.** `EstimateAbilityDamageRaw` calls `DamageMetamagic(ability)`, which calls native `AbilityData.HasMetamagic`. It reads actual metamagic data and special-metamagic state. `EvaluateDamageDice` caps the dice count before computing maximized/empowered damage. Native slot exports have `AvailableMetamagic = 0`, so normal UI availability must be distinguished from active mod-granted metamagic. | Make metamagic an explicit test dimension, including active/inactive special state and combined flags checked against native behavior. Do not add a new blueprint-based metamagic reader or claim player UI combinations are available without evidence. |
| **2.7: one `FusionKey` struct should replace all keys** | Identity gaps in some consumers are real and already documented. The proposed universal key is incomplete as a cast-context key: it omits payer/spellbook/item/metamagic/state distinctions where relevant. The resistance memo already uses exact object identities and an invalidation epoch; pending-cast keys already include configuration. A wide struct is not automatically faster. | Require consistent configuration semantics and frozen cast attribution, but select representation per lifetime and domain. Retain correct reference/epoch caches. Benchmark wider value keys only at demonstrated allocation sites. Produce a field-use audit rather than mechanically replacing every `ability.Blueprint` reference. |
| **2.7: any holder-blueprint read is wrong** | **Overbroad.** Some geometry sites are wrong, including the confirmed cone handoff. Other reads are deliberately native: action ownership, source identity and the inspected swarm vulnerability rule have holder-specific semantics. | Classify each site as holder, selected delivery, actual cast parameters, source payload or observation identity. Replace only a verified wrong-domain read. |
| **2.8: hoist dice/base values and reuse saves/SR** | Useful with dependency proof. Some values read target properties, target buff ranks, aim, shared state or provider previews. A single save probability cannot represent a genuine nested save with a different DC/state. SR memoization and target-free context reuse already exist. | Cache only proven invariant raw amounts; keep target reductions/bonuses live. Memoize by actual save node/DC/state when applicable. Avoid adding duplicate memo layers. Hoist within a synchronous, invalidated forecast scope rather than a permanent actor cache. |
| **2.8: dominance pruning and hot-path instrumentation** | Potentially helpful, but unsafe as a blanket rule. A lower-scoring low-tier candidate may still control Conservative gating; a boss candidate or caster benefit may matter after target effects are zero. Exhaustive per-effect timing and formatting could recreate logging costs. | Start with reuse and safe zero-benefit exits. Require proofs before nonzero dominance pruning. Collect bounded aggregate counters/timers only when diagnostics are enabled; preserve special candidate roles and ordinary-path cost. |
| **2.9: all rejection reasons and attribution** | Correct and already in the full plan. The practical improvement is to distinguish “has this blocker” from “this is its only blocker.” The latter estimates what a particular change could actually unlock. | Add blocker co-occurrence/sole-blocker counts, separate actual player configurations from static templates, and report unassessed live aim/value states honestly. Do not run expensive combat probes from a catalogue/UI repaint. |
| **2.10: earlier live validation** | Sensible for qualifying gameplay and installed-mod assumptions. The review's old 599-test figure is not the current baseline; the v0.3.52 receipt records 787 unit tests. Neither count proves gameplay. Natural in-game events should validate predictions; do not inject Rulebook rolls into forecasting. | Add an early baseline/cone smoke checkpoint and per-mechanism gameplay qualification. This does not block offline research or preparation of later slices while the author cannot play. Unplayed changes remain explicitly unqualified for gameplay acceptance. |
| **2.10: shadow table for every option** | Useful diagnostic intent; a full second decision pass or unbounded option×target dump is unsuitable. The original plan already specified the winner and a bounded runner-up. | Allow an opt-in, bounded one-decision capture of results already computed by the normal decision, with omission counts. Do not add a parallel shadow AI or repeated rule/context/path queries. |
| **Section 3: branch-outcome vector** | Useful for nonlinear utilities, already central to F3. Two corrections matter: linear expectations can be added even when effects are correlated, and resource/action costs must not be charged per recipient or per branch. | Preserve branches for kill/overkill/overlap/survival and other nonlinear consequences. Keep ordinary recipient forecasts local rather than enumerate every target's save jointly. Apply cast-level costs once; model genuinely shared pools/caster benefits separately. |

## Resulting revisions

The full revised plan now makes shared-math boundaries, time-based marginal control, simple-support scope, one-aim secondary effects, key lifetimes, dependency-safe optimizations and early gameplay qualification explicit. It also preserves behavior that the review incorrectly suggested was missing.

The original F0→F1→F2→F3 priorities remain. No two-target search, blanket key replacement, compulsory full-engine rewrite, repeated Rulebook preview, unbounded shadow log or new runtime code is introduced by this review task.
