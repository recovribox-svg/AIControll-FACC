## Source-confirmed candidate interaction deltas

### DarkCodex burn properties: material limit for the selected burn batch

At the checked DarkCodex commit, [`DarkCodex/Kineticist.cs`, `CreateMindShield`](https://github.com/Truinto/DarkCodex/blob/d02df11ab8f04add794b5a6da4c675e40e055889/DarkCodex/Kineticist.cs#L826) mutates the existing Psychokineticist burn buff's `ContextRankConfig`: `m_StepLevel = 1` and `m_CustomProperty` references a newly created unit property using `CodexLib.PropertyMindShield`.

The fetched [`CodexLib/Components/PropertyMindShield.cs`](https://github.com/Truinto/DarkCodex/blob/d02df11ab8f04add794b5a6da4c675e40e055889/CodexLib/Components/PropertyMindShield.cs) returns native `AcceptedBurn`, doubled only when the owner lacks its configured Mind Shield fact. Therefore a reader restricted to `KineticistBurnPropertyGetter` must **not** pretend to understand this patched property, use an archetype/main-stat heuristic, or silently forecast the unpatched two-per-burn rank. Installed patch state and feature transitions matter. Supporting only proved native property shapes is a valid explicit boundary; it does not establish support for this modded one.

**Mind Shield OFF gate verified in the checked v1.9.6 source:** [`Main.cs:658`](https://github.com/Truinto/DarkCodex/blob/d02df11ab8f04add794b5a6da4c675e40e055889/DarkCodex/Main.cs#L658) calls `LoadSafe(Kineticist.CreateMindShield)`. [`LoadSafe:1108–1125`](https://github.com/Truinto/DarkCodex/blob/d02df11ab8f04add794b5a6da4c675e40e055889/DarkCodex/Main.cs#L1108) resolves `Kineticist.CreateMindShield`, calls `CheckSetting`, and returns before `action()` when disabled. [`PatchInfoCollection.SetEnable` and `IsDisenabled`](https://github.com/Truinto/DarkCodex/blob/d02df11ab8f04add794b5a6da4c675e40e055889/DarkCodex/PatchInfoAttribute.cs#L143) store disabled options in the settings blacklist, which takes priority. Thus OFF at blueprint initialization skips the **whole creation method**, including the Psych burn-rank custom-property replacement, rather than merely withholding a selectable feat. The reported OFF configuration therefore makes the supplied native property shape expected, conditional on a startup/restart with that setting. The GUI marks option changes as requiring restart (`Main.cs:205–206`); changing the option after initialization does not itself undo an already patched in-memory graph. The actual loaded graph remains unverified.

Other inspected source/search evidence: `PatchVarious` applies configurable Psychokineticist main-stat changes; `PatchDarkElementalist` changes Soul Power to a free, fast-animation, non-full-round action restricted to out of combat. Main stat, visible class name and remembered action type are thus inadequate contracts. This programme should keep reading actual active parts/action types and preserve existing Soul Power native filtering.

### TTT resources, Magus and cross-class casting

The fetched [`TabletopTweaks-Core/MechanicsChanges/ActivatableAbilitySpendLogic.cs`](https://github.com/Vek17/TabletopTweaks-Core/blob/e76594f61b539c5243f74f150bb7afee604e1a48/TabletopTweaks-Core/MechanicsChanges/ActivatableAbilitySpendLogic.cs) defines an Aeon Gaze spend type and packed custom Crit spend amounts, patches availability/spending and `ActivatableAbility.ResourceCount`, and handles `FreeBlueprint`. For custom crit-spend types, ResourceCount becomes the affordable number of triggered uses, rather than a per-round duration. A universal `ResourceCount == rounds` assumption therefore fails for both native and patched event-spend contracts. Native enum inspection alone cannot certify every installed custom spend type.

Fetched [`TabletopTweaks-Base/Bugfixes/Classes/Magus.cs`](https://github.com/Vek17/TabletopTweaks-Base/blob/76c555f1f62f1f9c6fe4b378634c14ffdfec0c7c/TabletopTweaks-Base/Bugfixes/Classes/Magus.cs) conditionally sets Spell Combat and Spellstrike `DeactivateImmediately = true`, adds mutual removal to elemental versus burst enchantment buffs, changes prerequisites/progression and patches selected archetypes. This reinforces preserving internal toggle exclusions until exact patched command/continuation semantics are established; removing exclusions alone is unsafe.

Fetched [`NewContent/MagusArcana/BroadStudy.cs`](https://github.com/Vek17/TabletopTweaks-Base/blob/76c555f1f62f1f9c6fe4b378634c14ffdfec0c7c/TabletopTweaks-Base/NewContent/MagusArcana/BroadStudy.cs) creates level-6 Magus arcana selections with `BroadStudyComponent.CharacterClass` for other spellcasting classes. A future Magus contract cannot assume only a Magus spellbook can participate. Actual selection, book and enabled content are required. Merely finding the component does not prove its actor has it or execution succeeds.

### Isekai class labels and inherited mechanic provenance

Both fetched [`KineticDarkElementalistLegacy.cs` in the original source](https://github.com/JohN100x1/IsekaiMod/blob/32ff23ead79e7e65830a4a3d02e23058bdb1631b/IsekaiMod/Content/Features/IsekaiProtagonist/InheritedClassFeature/KineticDarkElementalistLegacy.cs) and the [checked fork](https://github.com/LionheartGames/PathfinderWOTR-IsekaiMod/blob/ffc0f2c7d7fe4646403ef9c07f36cdfb613fcd30/IsekaiMod/Content/Features/IsekaiProtagonist/InheritedClassFeature/KineticDarkElementalistLegacy.cs) create a “Kinetic Legacy - Soulbinder” progression derived from the Dark Elementalist archetype, with `GiveFeaturesForPreviousLevels` and helpers patching references to Isekai Protagonist's class. This independently establishes a plausible source mechanism for native kinetic parts arriving through a different class progression. It does **not** identify which legacy is selected in the current save or prove what those helper implementations/current forks do at runtime.

The checked fork's Info.json declares a TTT Core dependency and load-after relationships including TTT Base, DarkCodex, TomeOfTheFirebird and MysticalMayhem. Load order and post-initialization component mutations belong in installed evidence. A base-game Classes export alone cannot inventory dynamically generated mod progressions.

### Psionics marker ranks and custom resource actions

Fetched [`PsionicsCode/Buffs/PsionicFocus.cs`](https://github.com/TehFlaminTaco/Psionics/blob/01a00dd16c2f279fe637acc663a2fa28627b6a77/PsionicsCode/Buffs/PsionicFocus.cs) defines custom `SpendPsionicFocus` ContextAction and `PrerequisiteHasPsionicFocus` caster restriction. The focus buff uses rank stacking. Spending removes/deactivates it at the last rank or removes one rank, so simple buff presence is not the entire expenditure/continuation contract.

Fetched [`GainPsionicFocusAbility.cs`](https://github.com/TehFlaminTaco/Psionics/blob/01a00dd16c2f279fe637acc663a2fa28627b6a77/PsionicsCode/Abilities/GainPsionicFocusAbility.cs) creates elemental variant abilities, Standard with `IsFullRoundAction = true`, permanent focus application, custom `StripElementalFocus` and elemental focus replacement. Existing modern held-state support must be preserved; a generic buff value is insufficient to certify the custom action's cascade, rank handling and restoration. Current mod DLL/runtime graphs are needed to test these custom types offline and verify active author behavior. This source version need not match the later historical trance investigation.

### TomeOfTheFirebird composed performance grants

Fetched [`New Content/Feats/DiscordantSong.cs`](https://github.com/pheonix99/TomeOfTheFirebird/blob/8018d5d388ef4b746e74b196d7f55e7d64877861/TomeOfTheFirebird/New%20Content/Feats/DiscordantSong.cs) creates friendly/hostile carrier areas, conditional ally/enemy buffs and `AdditionalDiceOnAttack`; ranged extra dice require the target to carry the hostile area buff. It then adds `BuffExtraEffects` to selected existing performances and conditionally exposes the feat via settings. This is a concrete partner/recipient/target dependency signature for the grant-stage roadmap, not proof that the author selected it or that the current reader appraises the complete composed mechanism.
