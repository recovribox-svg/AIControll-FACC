# Summon control: implementation plan for Claude

**Plan only; no feature code is implemented here.** Checked development **`44b224f5af76dc5f5ae6086d6abbfbdeac790627`**, manifest **0.3.30**, after Claude integrated PRs #21–#45. Refresh development before implementation. Claude owns implementation/integration; Codex continues with focused reviews and interim fixes on separate task branches. Source evidence, input hashes and native-method identities are in [SUMMON_CONTROL_EVIDENCE.json](competence/SUMMON_CONTROL_EVIDENCE.json). `N1`–`N8` below refer to that file's native evidence records, not to hypothetical APIs.

## 2. First implementation slice

One opt-in feature PR: **direct, linked summons of an enabled main character/current party companion, during combat, through the current tactical engine in TB and RT**. One global `ControlSummons = false` checkbox beside companion control; omitted JSON loads false; add the existing English/Korean control-block strings. Explain the RT legacy-engine limitation in its help. Add no summon rows to the character catalogue; explicitly skip non-pet summons if another mod exposes them through `PartyCharacters`, before its settings upsert. Leave `Info.json` unchanged ([settings](../Settings/ModSettings.cs#L350), [control UI](../UI/MainUI.cs#L201), [catalogue](../UI/MainUI.cs#L572)).

Scope is based on native parts and capabilities. Pets/mounts retain their existing path; enemy/neutral, unlinked/scripted, nested, swarm and otherwise ineligible summons retain the game brain. The proposed first slice deliberately rejects **summons of summons**, instead of adopting them through an arbitrary two-hop walk. Direct native/Demonology creation is proven; nested adoption adds ownership cases without being needed for that path (N4–N5). If the TB bridge below fails its phase/termination probes, keep the whole feature off and reduce the delivered activation to RT; do not substitute a getter patch to get a green checkbox.

## 3. Gate and settings contract

Introduce a small `GameInterface/SummonControl.cs` resolver, separate from scoring. Check pets first, so a unit carrying both parts preserves the old pet path. For an ordinary summon, require: mod and current mode enabled; `ControlSummons`; live in-game combat actor with usable view/body/brain; player faction; conscious/not finally dead, not detached/panicked, no `PreventDirectControl`, no confusion state requiring game control; linked non-self summoner; no active swarm body/round-attack mechanics. Reuse the active-fact component reader in [SwarmFacts](../Tactics/CombatMath.SwarmSources.cs#L26), exposing a narrow read, without an enemy scan or creature-name list. Swarms are not universally turnless: native `WillTakeTurn` filters status, not creature kind (N6).

The direct summoner must be the main character or a member of `Player.PartyCharacters`, be alive/conscious/player-controlled in the native sense, and satisfy its global main/companion switch plus an **existing** enabled character row. Use `TryGetValue`, not `ShouldControlUnit(owner)` or an upsert. An absent owner row defers adoption until the ordinary owner path initializes it. Reject a parent carrying the summon part, self-link and null parent without recursion. RT additionally declines when `RealTimeLegacyEngine` is selected; TB retains the current tactical engine. Check these same conditions at issue, not only when first adopted ([ShouldControlUnit](../GameInterface/CustomBrainPatch.cs#L139), [legacy dispatch](../GameInterface/RealTimeController.cs#L367); N4–N5).

Handle non-pet summon actors before the existing direct-control/per-character upsert branch of `ShouldControlUnit`. Ineligible summons return false **even when another mod makes them clickable**. Ordinary characters and pets retain the old branch. This is the intended ToyBox coexistence contract; it requires no ToyBox reference. The supplied ToyBox has a controllability postfix, but no live interoperation test has occurred (N8).

**Use one non-persisting settings-read path everywhere that can read a temporary actor/recipient:**

| Policy | Summon behavior |
|---|---|
| Ownership and AI enable | Existing owner row and global control/mode switches; never a summon row. |
| Combat view | Mixed range, default DPS role, Pure Mage **false**; inherit the owner's `AvoidFriendlyFire`, `HealAtHPPercent` and `SpellPolicy`. This chooses no creature-specific style and preserves the summon's weapon/spell competition. |
| Ability blocklists | Existing compiled **shared + owner** scope, using the owner's ID in `UserAbilityPolicy.ScopeFor(UnitEntityData)`; not an ID alias for inventory, spellbooks or memory ([ScopeFor](../Tactics/UserAbilityPolicy.cs#L90)). |
| Abilities/resources | Discover the summon’s own abilities and spellbooks only, as `AbilityDiscovery.Gather` already does; never substitute the owner ([Gather](../Tactics/AbilityDiscovery.cs#L111)). |
| Items | The first slice chooses no source-item/material-consuming ability for a summon. Keep `ConsumablePolicy.IsAllowed` in the ordinary path; no borrowing of party/owner items ([policy](../Tactics/ConsumablePolicy.cs#L39)). |

Create the temporary combat view once per actor in a weak-keyed state record and refresh the small inherited scalar set on access. Never mutate or serialize the owner row; do not copy its role/range/Pure Mage settings or expose this view in the UI. Route `BuildContext`, `ProgressiveGate.IsEnabledFor`, `PureMagePolicy.SettingsFor`, and both `PreBuffAnalyzer` recipient reads through the non-persisting read. Temporary summon recipients need a default read even when the feature is off, since another controlled caster can inspect them. Leave `ModSettings.GetOrCreateSettings` and ordinary/pet behavior intact. Its dictionary is serialized, so “not explicitly calling Save” does not solve the leak ([GetOrCreateSettings](../Settings/ModSettings.cs#L485)).

## 4. Hooks and completion

**RT:** extend the existing `TickBrain_Prefix` gate, then use `RealTimeController.ProcessUnit` with its existing cooldown, pending-command, Wrath handoff and budget gates. Do not call `Decide` directly or add a scheduler. Force no legacy scorer onto a summon (§3; [prefix](../GameInterface/CustomBrainPatch.cs#L43), [ProcessUnit](../GameInterface/RealTimeController.cs#L119)).

**TB: use the natural AI route, leaving controllability unchanged.** Native `Prepare` resets actions, ticks new-round effects and calls `ForceTick` **before** setting `Status`; a normal summon then enters `Acting`. Native `Tick` invokes the brain again when that actor is idle (N1). Implement this sequence:

1. A narrowly gated `TurnController.Prepare` **postfix** services an eligible, non-controllable current summon only after native preparation has completed and status is `Acting`. The `TickBrain` callback during preparation suppresses its native brain but does **not** score in `Scrolling` or partly initialized state.
2. Subsequent TB `TickBrain_Prefix` calls for that same current, non-controllable summon in `Acting` forward to the **existing** `TurnBasedController.ProcessTurn`. Return false after claiming service; enemies/other units use the original route. A current-turn/reference + frame stamp prevents duplicate driver service in the same frame. This is an entry adapter, not another decision loop.
3. The existing `TurnControllerTick_Postfix` continues driving directly controllable units, including an eligible ToyBox-clickable summon. It must not also score a native non-controllable summon serviced above.
4. Factor the existing completion handling for reuse. A native-summon `EndTurn` result marks its turn memory finished. In the Tick postfix, service completion even if the native brain is no longer called: current owned rider only, valid `Acting` state, command/queue/acting checks, existing stranded-idle-command handling and `ReadyToEndTurn` projectile/get-up/idle wait with its **4 s cap**, then `ForceToEnd(true)`. Do not require `CanEndTurnAndNoActing` for this actor; it always rejects native non-controllable units. If native code has already entered Ending/Ended, leave it alone (N2; [current completion](../GameInterface/CustomBrainPatch.cs#L342), [ReadyToEndTurn](../GameInterface/CustomBrainPatch.cs#L299)).

No `Status` setter, getter override, faction/group/party edit, turn-panel injection or teleport. A getter override would unnecessarily change selection/UI and native action branches (N5, N8). No direct `Decide` in a prefix: both adapters call an existing driver. All commands still go through [CommandDispatcher.Run](../GameInterface/CommandDispatcher.cs#L111).

Only activate TB summon interception after both required patches bind successfully. A service exception must preserve one owner of the command stream: mark an already-claimed turn failed/finished for bounded completion, rather than returning to the native brain after issuing a command. Unclaimed/ineligible actors use native behavior. Turning off the feature/mode or losing the owner returns a native non-controllable rider to native handling; it has never been forced into Preparing. This must be demonstrated, not inferred from a successful build.

## 6. Performance contract

Keep **3 ms** RT admission, current intervals and all selected-path/search caps. A started decision can exceed the budget; a fast pack can share a frame. `ClearAttackCache` runs per decision, so only blueprint metadata is shared across actors ([Decide](../Tactics/TacticalEngine.cs#L284)). A melee summon uses ordinary live-body math; a caster can trigger many per-target forecasts. Neither has a measured new-feature cost yet.

The actual shifter1 log (SHA-256 in the evidence file) says at line 2951: `[Perf] real-time: 180 decisions, median 30.2 ms, 95% 196.7 ms, slowest 1301.5 ms`; line 1033 reports TB median **95.6 ms**, p95 **318.0 ms**, slowest **2008.4 ms**. These are mixed-party figures from a played older build, **not summon benchmarks**. The largest three spikes overlap GC; a heap delta is not an allocation count. Existing slow rows start at 250 ms ([Decide](../Tactics/TacticalEngine.cs#L303)); current medians combine all actors ([FightStats](../Tactics/FightStats.cs#L174)).

Extend those existing timing summaries with summon/ordinary cohorts per mode, cold-first versus subsequent counts, and bounded verbose adoption/frame/queue traces for the pack test. Measure gate/bridge overhead separately because it occurs outside the Decide timer. Reuse native fact snapshots, weak actor state and decision-local caches; no hot-loop logging or extra forecast merely for diagnostics. Preserve arithmetic and budget behavior.

**Lifetime work is part of this slice:** `_lastDecisionTime` and `_unitPhaseOffsets` are strong ID dictionaries, and `ClearCache` has no production caller at this baseline. Store summon pacing fields in the same weak actor state instead, with the same read/write/offset semantics, while companions keep their existing dictionaries. Clear the existing pending-service queue at combat end; it contains future service requests, not issued commands. Keep expired-entry revalidation. No new queue or broad movement-cache reset ([pacing fields](../GameInterface/RealTimeController.cs#L60), [ClearCache](../GameInterface/RealTimeController.cs#L1165)).

Accept performance only after matched off/on combat replays: party/cohort medians, p95, slowest, first-frame admissions and gate allocations. Native AI is not timed by `[Perf]`, so use an external Unity/frame capture for the actual baseline hitch comparison. An expensive supported caster may still be unsuitable for a large pack; leave the setting off by default and report that finding, not a fabricated speed promise.

## 7. Failure acceptance

* **Frozen/empty turn:** no controllability change; no actor scoring inside incomplete Prepare; one driver owner; the shared completion path services no-option, exception, exhausted budget and stuck projectile cases. Confirm disabled-mode and mid-turn ownership loss. A failed hook/turn lifecycle probe blocks TB activation (§4; N1–N2).
* **All paths rejected:** retain native dispatcher safety and the approved three-check/idle-advance policy. Log the actual rejection/choice/end; do not invent a route or relax hazards to make a demo move ([approach validation](../Tactics/TacticalEngine.ApproachValidation.cs#L39)).
* **Spell steals a full attack:** compare existing candidate values and actual actions. Concrete cases are Vavakia's Enervation/breath and Lilitu's **DominateMonster**, which the existing audit reads as hard control. An owner may not want that spell; its owner blocklist must apply. There is no evidence here that those choices are overvalued, so add no creature/spell bonus, blacklist or anti-buff rule (blueprint/audit evidence; [blocklist](../Tactics/UserAbilityPolicy.cs#L90)).

## 8. Implementation sequence, checks and replay

One feature branch/PR into development, with three internal commits: **policy/settings/exclusions**, **native lifecycle/RT pacing**, then **UI/diagnostics/tests**. Leave activation unavailable until its complete path passes. Update `CLAUDE.md` and append the implementation's own TACTICAL_AI section; §151 records only this plan. Refresh every referenced symbol if development moves.

Automated checks must exercise behavior boundaries, not just mirror boolean expressions:

* Pure ownership/policy cases: off/default JSON, owner switch and missing row, main versus companion, pet with both parts, hostile/charmed enemy owner, dead/unlinked/self/nested parent, swarm, mode/legacy, root Pure Mage + melee summon, inherited blocklists. Prove read-only policy resolution cannot insert IDs, including recipient reads with the feature off.
* Actor-free native/compiled-route checks: creation/part contracts, full hand+limb routine, Prepare/ForceTick ordering, no getter/Status patch, shared driver/dispatch/finish routes and default-off hook failure. Scheduling/state fixtures must cover new Prepare, repeated same-frame callback, Acting idle, useful quick followed by main, EndTurn/exception, queue-only wait, missing projectile completion, mode toggle and owner loss. Static checks still do not prove Unity execution.
* All existing unit/inventory tests; real-reference Release with **0 warnings/errors**; ProfileAudit and existing native/provider regressions with all inputs, including the author's Units/Buffs/Spells exports. Missing/known raw-export failures stay explicit. Verify exact new foreign member signatures. Keep original assemblies and offline stubs separate.

Play matched **TB and RT** with (1) one Leopard, then a melee pack, and (2) one Bralani; add a Demonology ritual summon to verify the supplied mod's runtime linkage. Capture a valid natural full attack, blocker/hazard/no-path, no legal ability, quick-plus-standard, caster buff/damage choice, settings off and both mode switches, owner AI/main-control off, owner death, despawn, nested/swarm rejection, Pure Mage owner, and owner-blocked Dominate on a mixed kit. Check summoned actors never use owner items/books or cast a recognized summon spell; pets and manual commands remain intact. Repeated summon/expire/rest cycles must leave no new summon IDs in saved settings and no retained pacing entries. Test ToyBox clickable summons separately and label it untested until actually run.

Keep startup MVID/commit/checksum identity for every test ZIP; do not bump the manifest for a test. Record `[Tactics]` choices, native turn progression and the actual cohort `[Perf]` rows. Stop expansion if melee safety or turn completion fails; investigate the bridge rather than retuning spell values.

## 9. Outside this change

No per-creature AI/tier scores, signature gaze/engulf/ray work, Shifter future-form projection, summon-duration multipliers, recursive/nested ownership, hostile/neutral adoption, native swarm actors, exploration/pre-fight automation, RT legacy extension, extra scheduler/budget, movement/target-commitment/retreat/pathfinder/stuck-policy changes, or ToyBox faction/UI/group/teleport features. No main/development push, merge, release or version bump by Codex. Existing path safety is reused; any later movement policy proposal stays separate.

The plan is supported by inspected code, native IL/decompilation and supplied blueprint/log evidence. **The feature itself is unimplemented and unplayed.** No additional files are required to begin this scoped implementation; live verification of the final bridge and each modded kit remains essential.
